# 第 9 课 · 渲染机制与性能优化

## 学习目标

- 说清楚组件重渲染的两种（且只有两种）触发方式：自身 state 变化、父组件重渲染。
- 理解"重渲染 ≠ 重绘 DOM"：重渲染只是重新执行函数 + diff，React 只把真正的改动提交到真实 DOM。
- 会用 `useRef + useEffect` 写一个渲染计数器，实测某个组件到底重渲染了几次。
- 知道 `React.memo` 的浅比较原理，以及为什么内联函数 / 内联对象会让它失效。
- 建立"默认不写，先测量"的优化心态，并理解 key 稳定性为何比 memo 更重要。

## 核心概念

### 组件何时重渲染

只有两种情况会让一个组件的函数体重新执行：

1. 它自己的 `setState` 被调用（state 变化）。
2. 它的父组件重渲染了（父组件函数重新执行，子组件的 JSX 被重新求值，除非子组件被 memo 且 props 没变）。

```jsx
function Parent() {
  const [tick, setTick] = useState(0)
  return (
    <>
      <button onClick={() => setTick(tick + 1)}>tick +1</button>
      {/* Parent 重渲染 → Child 跟着重渲染，哪怕 Child 完全没用到 tick */}
      <Child />
    </>
  )
}
```

注意：props 变化不是独立的触发条件——props 变了，本质是父组件重渲染时传了新值。

### 重渲染 ≠ 重绘 DOM

"重渲染"是重新执行组件函数、生成新的虚拟 DOM 树，然后 React 和旧树做 diff，**只把差异部分**更新到真实 DOM。所以一个重渲染的组件如果输出没变，浏览器什么都不用做。React 的 diff 已经非常快，这就是为什么大多数"预防性优化"没有可测量的收益。

### React.memo 与浅比较

```jsx
const Child = memo(function Child({ items, onPick }) { ... })
```

`memo` 会对新旧 props 做浅比较，全部相等（`Object.is`）就跳过重渲染。但只要有一个 props 是引用类型且每次渲染都新建——比如内联箭头函数 `onClick={() => ...}`、内联对象 `{a: 1}`、未缓存的计算结果——浅比较必然失败，memo 形同虚设。所以 memo 通常要配合 `useCallback`（缓存函数引用）和 `useMemo`（缓存计算结果 / 对象引用）一起用。

### 正确心态：默认不写，先测量

`useMemo` / `useCallback` / `memo` 本身有成本（存依赖数组、每次渲染做比较、代码更难读）。它们不是"写上就更快"的护身符。正确流程：

1. 感觉慢（或用户反馈慢）；
2. 用 **React DevTools 的 Profiler** 录一次交互，看哪个组件渲染耗时最长、渲染了多少次；
3. 只针对实测确认慢的那个组件优化；
4. 再录一次，确认确实变快了。

### key 稳定性：比 memo 更常见的性能杠杆

列表渲染时，key 决定了 React 是"复用已有 DOM 和组件状态"还是"卸载重建"。用数组下标当 key、或用 `Math.random()` / `Date.now()` 生成 key，插入 / 过滤时会让 React 认为整列表都是新元素，全部重建——丢输入框状态、丢动画，还更慢。key 的唯一要求：**在同一列表里稳定且唯一，和元素内容绑定**。

## 代码导读

### `src/components/lesson9/RenderCounter.jsx`

渲染计数器，本课的"测量工具"。关键设计：

- 用 `useRef` 存次数：改 ref 不触发重渲染，不会造成"计数导致渲染、渲染导致计数"的死循环。
- 计数发生在渲染期间（函数体执行时），`console.log` 每次都实时打印——控制台日志是比页面数字更真实的观测手段。
- 页面数字直接显示 `countRef.current`，所以永远比真实值慢一拍。为什么不搬进 useState？因为"更新显示 → 新渲染 → 计数 +1 → 又更新"会无限循环，页面卡死——这是做计数器时最真实的坑。同时也直观看到：ref 适合存不需要显示的值，一旦要显示就得付代价。

### `src/components/lesson9/ExpensiveList.jsx`

被 `memo` 包裹的"贵的"子组件（1 万项数据、求和结果），渲染时打日志。注意它渲染前 5 项就够演示了——演示性能时别把页面卡死。

### `src/components/lesson9/PerfDemo.jsx`

三段对比，是本课的主菜：

- **第一段 BareChild（裸子组件）**：没 memo。点"加一个无关 tick"，父组件 `PerfDemo` 重渲染，它跟着重渲染——渲染计数 +1，虽然 tick 和它毫无关系。
- **第二段 MemoChild（优化版）**：`memo(ExpensiveList)` + `useCallback` 包 `handlePick` + `useMemo` 包 1 万项求和。点"无关 tick"它纹丝不动（props 浅比较全相等）；点"改关键字"它才重渲染，而且重渲染时求和也不会重跑（`useMemo` 空依赖缓存）。开着控制台，看日志和时间戳验证每一步"谁重渲染了、谁被拦下了"。
- **第三段心态小结**：默认不写、先测量，以及 key 稳定性。

两个易被忽略的细节：① 1 万条数据放在**模块顶层**只造一次，如果放在组件函数体里，每次渲染都重建数组，"优化"就自我失败了；② 求和的 `useMemo` 依赖数组是 `[]`，因为数据是常量——依赖数组要诚实，写上不依赖的东西反而制造 bug。

### `src/pages/Lesson9.jsx`

页面入口，先用两段话建立"何时重渲染 / 重渲染 ≠ 重绘"的心智模型，再交给 `PerfDemo`。样式在 `src/pages/lesson9.css`（计数徽章、演示子组件边框）。

## 动手试一试

1. **实测裸组件的代价**：打开 React DevTools 的 Profiler，点第 9 课页面的"加一个无关 tick"，看 BareChild 和 MemoChild 的渲染记录差异（一个亮、一个灰）。再试着给 BareChild 包上 `memo`，观察变化。
2. **亲手破坏 memo**：在 `PerfDemo` 里把 `handlePick` 改回内联函数 `<ExpensiveList onPick={(v) => setPicked(v)} ...>`，用渲染计数验证 memo 失效，然后恢复。
3. **优化一个真实慢的过滤列表**：在本页加一个"过滤 5 万个单词"的搜索框（输入关键字，列表实时过滤）。先用 Profiler 测量输入时的卡顿来源（是每键重算过滤？还是列表项太多导致 DOM 提交慢？），再决定用 `useMemo` 缓存过滤结果、`memo` 列表项，还是虚拟截断只渲染前 N 条——每种方案都测一次再下结论。

## 易错点

1. **把渲染计数搬进 useState 显示**：setState 更新显示 → 触发新渲染 → 计数 +1 → 又 setState，无限循环页面卡死。计数只能放 ref，显示直接用 ref 值（接受慢一拍），或用控制台日志观测。
2. **内联函数让 memo 失效**：`<Child onPick={() => doIt()} />` 每次渲染都是新函数，`memo` 的浅比较必败。现象：明明包了 memo，子组件还是每次都重渲染。
3. **把"每次都新建"的数据放进组件体**：`useMemo(() => sum(BIG), [BIG])` 里 `BIG` 是组件内 `const BIG = [...]`，每次渲染都是新数组引用，依赖比较永远不等，memo 白算。常量数据提到模块顶层。
4. **用下标当 key 还做插入 / 删除 / 过滤**：现象是删中间一项，后面所有项的状态（输入框内容、勾选）串位。原因：下标 key 让 React 复用了错误的元素。
5. **为了"性能"到处包 useMemo/useCallback**：代码可读性下降，性能却测不出变化。Profiler 里不亮的组件不需要任何优化。

## 自测题

1. 一个组件的函数体重新执行，可能有哪几种原因？
2. 为什么说"props 变化导致重渲染"这句话不够准确？
3. `React.memo` 的浅比较对哪种 props 必然失败？举两个例子。
4. 列表用 `Math.random()` 生成 key 会有什么后果？为什么？

<details>
<summary>参考答案</summary>

1. ① 自身 state 变化；② 父组件重渲染（且自己未被 memo 拦下）。没有第三种。
2. props 变化不是独立原因：本质是父组件重渲染时重新执行了子组件的 JSX。即使 props 没变，父组件重渲染也会带着子组件重渲染（除非 memo）。
3. 引用类型且每次渲染都新建的 props：内联函数 `onClick={() => ...}`、内联对象 / 数组字面量、每次渲染重新计算的派生值（未 useMemo）。
4. 每次渲染 key 都不同，React 认为整列表都是新元素，全部卸载重建：DOM 操作暴增、组件状态（输入框、勾选）全部丢失。key 必须稳定且和元素内容绑定。
